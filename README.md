# Roomtone

A private, browser-based intercom for your local network. Give each browser a room, then call another room with two-way voice or video. A room can have several devices: all available devices ring and **the first to answer connects**. Media travels directly between the two browsers using WebRTC; the server coordinates presence, ringing and connection setup. Optional iPhone lock-screen alerts use outbound Apple Web Push; the app, call signaling and media remain on your LAN. No cloud account, recording service or external media relay is used.

## What you need

- A computer or NAS on your LAN with Docker Engine and the Docker Compose plugin, kept running during calls. Reserve a stable LAN IP for it in your router. The included configuration publishes only HTTPS on host port **8443** by default (configurable with `HTTPS_PORT`); it does not claim host ports 80 or 443.
- Browsers on client devices that support WebRTC and can reach one another over the LAN. A microphone is needed for voice; a camera is optional for video. Keep the app tab open while expecting calls unless you enable the optional iPhone Home Screen push alerts described below.
- For optional locked-iPhone alerts: iOS **16.4+**, Roomtone **installed to the Home Screen**, notification permission, and outbound internet access from both the Docker host and iPhone to Apple's push service (`*.push.apple.com`, HTTPS/TCP 443). No extra inbound port or public DNS name is required. The private-IP/local-CA combination must be confirmed on your own iPhone before depending on it.
- Permission to install a local root certificate on **each client device**. This is necessary because browsers will not offer camera/microphone access to an ordinary `http://192.168.x.x` page. The included Caddy container creates local HTTPS for your LAN IP. See [MDN's secure-context requirement](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) and [Caddy's local HTTPS guide](https://caddyserver.com/docs/automatic-https#local-https).

## Deploy with Docker Compose

1. Copy `.env.example` to `.env`. Set `LAN_HOST` to the Docker host's **stable LAN IP**, such as `192.168.1.50`. Set `ADMIN_PIN` to your own unique secret of at least six characters. Use a longer random passphrase when possible. `HTTPS_PORT=8443` is the default; if another project uses it, choose another unused host port such as `9443`. Restrict the file to the host administrator (`chmod 600 .env` on Linux).
2. In this folder, run:

   ```bash
   docker compose up -d --build
   ```

3. Check that it started. Replace the IP below with your `LAN_HOST`, and change `8443` if you configured another `HTTPS_PORT`:

   ```bash
   docker compose ps
   curl -k https://192.168.1.50:8443/healthz
   ```

   The `-k` flag is only for this first server-health check, before trusting the local certificate. A healthy response is `{"status":"ok"}`. **Do not treat a browser certificate-warning bypass as a substitute for installing the CA.**
   Caddy is configured with `default_sni {$LAN_HOST}` because TLS clients commonly omit SNI when connecting to a numeric IP. Without that fallback, `curl` can fail with `tlsv1 alert internal error` before reaching the app. If TLS succeeds but the app is unavailable, inspect `docker compose logs --tail=100 app caddy`; a restart-looping app is a separate problem.
4. Export the **public root certificate** generated by Caddy (not its private key):

   ```bash
   docker compose exec -T caddy cat /data/caddy/pki/authorities/local/root.crt > roomtone-ca.crt
   ```

   If the file does not exist yet, visit the HTTPS URL once with `curl -k`, then retry. Copy `roomtone-ca.crt` to each client over a trusted local channel and add it to that device's trusted root authorities. The Caddy root key remains in the private `caddy_data` Docker volume; never distribute it.
5. On each browser device, open **`https://<LAN_HOST>:8443/`** (substitute your configured `HTTPS_PORT` if different). Use the HTTPS scheme and port explicitly; no host port 80 redirect is published. The IP address must match `LAN_HOST`, and the browser should show a normal trusted HTTPS connection. Choose a device name and room, then enter the administrator PIN to assign it. Do the same on another device in another room; it should appear online immediately. You can edit the four starter rooms or add/delete rooms in **Manage rooms**.
6. Tap or click the app once to allow audible ringing on that browser. If the dashboard offers **Enable ring sound**, use it. Allow the browser's microphone/camera permission when placing or answering a call.

**Updating an existing checkout:** Run `git pull --ff-only`, optionally add `HTTPS_PORT=8443` (or another unused port) to your existing `.env`, then run `docker compose up -d --build`. The default is 8443 even if that line is absent. This recreates Roomtone's containers without stopping unrelated Docker projects and preserves its named data and Caddy CA volumes. If the chosen host port is occupied, change `HTTPS_PORT` and retry; you do not need to change the Caddyfile.

### Installing the local CA on clients

The exact menus differ by OS version. Use the device's **trusted root CA** store, not merely a one-time browser warning exception.

| Client | Typical path |
| --- | --- |
| iPhone / iPad | Open the certificate/profile on the device; install it under **Settings → General → VPN & Device Management**, then enable **full trust** under **Settings → General → About → Certificate Trust Settings**. |
| macOS | Import `roomtone-ca.crt` into Keychain Access (System keychain) and set it to **Always Trust**. Restart the browser if necessary. |
| Windows | Import it into **Trusted Root Certification Authorities** for the local computer or current user. Restart the browser. |
| Android | Install a CA certificate in Settings' security / encryption-and-credentials area. The path and browser trust behavior vary by Android version and browser. |
| Linux | Add it to the system trust store using your distribution's CA procedure, and ensure your browser uses that store. |

After importing, open `https://<LAN_HOST>:8443/` again (or use your configured HTTPS port). If the browser still reports an untrusted or mismatched certificate, check that the IP in the address bar matches `LAN_HOST`, the CA file came from this exact Caddy instance, and the browser was restarted. On iOS, verify the additional **full trust** switch. Changing only `HTTPS_PORT` does not require a new CA; the certificate covers the IP address, not the port. If you later change the Docker host's IP, update `LAN_HOST`, restart the stack and revisit the new IP; Caddy can issue a new leaf certificate under the same persisted CA.

## iPhone lock-screen alerts (optional)

1. On your iPhone, confirm the local CA is **fully trusted** and the app opens in Safari without a certificate warning. In Safari, tap **Share → Add to Home Screen**, then launch **Roomtone from its Home Screen icon**. A Safari tab alone cannot receive Home Screen push while locked. If the installed copy starts unassigned, give it a device name and room using the administrator PIN; Safari and the Home Screen copy may have separate storage.
2. In the installed app, tap **Enable alerts** in the Lock-screen alerts panel and allow notifications. If the button is unavailable, check your iOS version, that you launched from the Home Screen icon, and that the certificate is trusted. In **Settings → Notifications → Roomtone**, allow Lock Screen alerts and sounds. Focus modes, Silent Mode and other iOS settings can suppress sound; these are ordinary notifications, **not** CallKit phone calls.
3. From a different room, place a voice or video call while this iPhone is locked. Roomtone sends a short-lived, encrypted notification through Apple; **tap it, unlock the phone, then tap Answer call** in Roomtone. The first device in the room to answer wins. A push-enabled call waits up to **75 seconds**; a call to live-only devices still waits **45 seconds**. The iPhone must be on the reachable LAN when you open the app to establish voice/video, even if Apple delivered a notification over cellular.
4. Use **Turn off alerts** in the installed app to unsubscribe, or revoke a lost device from **Manage rooms**. A push subscription and VAPID signing keys are stored in the private `roomtone_data` Docker volume, so back it up alongside room assignments. The push payload contains an opaque call ID and expiry, **not room names or media**. Apple handles notification delivery; direct WebRTC audio/video is never uploaded to Apple.

If the server cannot confirm **Turn off alerts**, the panel says **Still turning alerts off** and retries your saved choice when the app reopens; notifications may continue until the server responds. If the server confirms off but the browser cannot clean up its local subscription, alerts stay off at the server and the browser retries cleanup later. Roomtone never silently restores alerts after an explicit opt-out; you must tap **Enable alerts** to restore them.

**Troubleshooting:** If the room shows “Alert available” but no iPhone notification arrives, inspect `docker compose logs --tail=100 app`. A `Push delivery failed` line points to blocked outbound HTTPS, an expired subscription or a push-service rejection. Ensure the Docker host can reach `*.push.apple.com` on TCP 443, and verify the iPhone has internet access and Roomtone notifications enabled. `VAPID_SUBJECT` defaults to this repository's public HTTPS URL; if you customize it, use your own **real public HTTPS contact URL or `mailto:` address**, never `localhost`. After changing `.env`, run `docker compose up -d --build`. A previously delivered notification may remain on the Lock Screen after another device answers; tapping it opens Roomtone, which will report that the call ended. Ongoing WebRTC media can still stop if you lock the screen mid-call.

References: [WebKit's iOS Home Screen Web Push requirements](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/); [Apple's server-side Web Push protocol](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), including the requirement to show visible notifications; and [the Web Push library's Apple VAPID contact guidance](https://github.com/web-push-libs/web-push/issues/947). An iPhone on a trusted private-IP certificate must still be tested on the actual LAN; these sources do not guarantee delivery in every network/browser configuration.

## Everyday use

**Room administration and assignments:** Room creation, editing, deletion and device registration/assignment require the administrator PIN. The browser's admin unlock lasts eight hours or until the server restarts. The PIN is not needed to place or answer calls after a device is assigned. Device identity is stored in that browser's local storage; clearing browser data creates a new device that must be assigned again. **Manage rooms** also lists registered devices and lets an administrator revoke a lost or retired device. Deleting a room unassigns its devices and ends any call involving it. The first run seeds Living room, Kitchen, Home office and Entryway as editable examples.

**Calling:** Select an online or **Alert available** room and choose **Voice call** or **Video call**. Live devices ring in the app; opted-in devices also receive a push notification, even if their app is currently open, so an iPhone will not miss the handoff to screen lock. The first answer connects and the others stop ringing. Declining on one device does not reject the call for the others. Rooms are treated as busy during ringing and while connected, so another call to/from either room waits until the current attempt ends. Calls time out after 45 seconds for live-only recipients or 75 seconds when push subscribers are included. Use the in-call controls to mute, toggle the camera where present, or hang up. A microphone-only device can answer a video call with voice while still receiving the other party's video.

**Network scope:** The app server and Caddy run only on your machine's Docker host. Docker binds the configured host HTTPS port (8443 by default) **only to the `LAN_HOST` IPv4 interface**, rather than all host interfaces. It does not publish host ports 80 or 443. Still, **do not forward the chosen port on your router** and use a host firewall to allow it only from trusted LAN subnets. Opt-in push makes outbound HTTPS requests to Apple or another browser push service; there is no cloud backend for app data, signaling or media. Devices must be able to connect directly over your network for WebRTC media: guest Wi-Fi isolation, client isolation, VLAN rules, host firewalls, or restrictive VPN policies can block calls even when both browsers can reach the app. No STUN/TURN relay is configured, intentionally. WebRTC media is encrypted in transit; the server never records it.

## Maintenance and backups

`roomtone_data` stores room names, device assignments, optional push subscriptions and the persistent VAPID signing key; `caddy_data` stores the local CA. Back up **both Docker volumes** if you want to preserve assignments and avoid re-trusting a new CA or re-enabling push on every client. Keep both private keys protected. To update, replace the source files and run `docker compose up -d --build`; to inspect logs, use `docker compose logs -f app caddy`. If you delete the Caddy volume, clients must trust the newly generated CA again. If you delete `roomtone_data`, device assignments and push subscriptions are lost and iPhones must be re-enrolled. To revoke trust later, remove Roomtone's Caddy Local Authority from each client's trusted roots.

The server stores device token **hashes** but the browser stores its own token locally. There are no user accounts; anyone with access to an already-assigned, unlocked browser can place calls. Only deploy this on a network and devices you trust.

## Develop and validate

Node 22 is recommended. Run `npm ci`, then `npm run dev` for Vite at `http://localhost:5173` and the Express/WebSocket server at port 3000. Localhost is a browser secure context, unlike a LAN HTTP IP. In **development only**, an unset `ADMIN_PIN` defaults to `123456`; set it explicitly for any shared environment. `npm run build` creates the production `dist/`. `npm test` checks API authorization, Web Push enrollment/offline ringing, service-worker notification handoff and multi-device signaling using a local mock transport—**it does not prove Apple delivered a notification to a real iPhone**. `npm run test:e2e` runs two real headless Chromium browsers with fake camera/microphone devices; it requires Chromium at `/usr/bin/chromium` and tests voice, video, and a microphone-only recipient.

## Boundaries

This is a one-to-one **room-to-room** intercom, not a native background phone service. An installed iPhone web app can receive an ordinary lock-screen notification, but cannot automatically answer or keep its WebRTC media alive while locked. Browser permission and autoplay rules can require interaction before sound or calls work; Focus and Silent Mode may suppress notification sounds. No calling across isolated network segments, no Internet media relay, no recording, no multi-party conference and no dedicated TURN server are included. Docker itself was unavailable in the development sandbox, so the Compose/Caddy configuration was parsed and Caddyfile-adapted, but a complete container launch must be verified on your LAN host, including a real locked-iPhone push delivery test.
